Лабораторная работа по сортировкам
Краткое описание что и как делалось - для защиты

Общая структура:
папка lab_sort/Tasks  - код на C++ (один .cpp на задание)
папка lab_sort/Data   - csv файлы с замерами времени (создаются запуском .cpp)
папка lab_sort/Graph  - python скрипты для графиков и png картинки

Во всех C++ файлах используются стартер-коды из методички:
 - вывод в файл через ofstream ("1.csv")
 - измерение времени через chrono::high_resolution_clock / get_time() в секундах
 - генерация случайных чисел через rand_uns(min,max) на основе default_random_engine
Сортировки написаны как отдельные функции void sort(vector<int>& a)
Чтобы компилятор не вырезал сортировку при -O3, после сортировки считается volatile сумма элементов.

Запуск: g++ -O2 Tasks/task0.cpp -o /tmp/task0 && /tmp/task0  (для task1 и task3 нужны разные флаги -O0 -O1 -O2 -O3)
Графики: python3 Graph/graph0.py  (требует matplotlib)

--------------------------------------------------------------------------------
ЗАДАНИЕ 0. Простые медленные сортировки O(N^2)
--------------------------------------------------------------------------------
Сделано: три сортировки - пузырек (bubble), вставка (insertion), выбор (selection).
Размеры: N = 500 .. 5000 шаг 500. Для каждого N 3 повтора и среднее.
Графики:
 - task0.png - обычный масштаб, три кривые. Пузырек самый медленный (парабола), вставка самая быстрая из трех, выбор посередине.
 - task0_loglog.png - двойной логарифм. Наклон всех трех прямых ≈2, значит log(t) = 2*log(N)+const, => t ~ N^2. Так проверяем что сложность O(N^2).

Что рассказать: пузырек делает ~N^2/2 сравнений и обменов, вставка быстрее на почти отсортированных, выбор всегда ~N^2 сравнений но мало обменов.

--------------------------------------------------------------------------------
ЗАДАНИЕ 1. Автоматическая оптимизация
--------------------------------------------------------------------------------
Сделано: одна сортировка (пузырек) измерена 5 раз с разными флагами: без флагов, -O0, -O1, -O2, -O3.
Для каждого флага отдельный бинарник: g++ -O0 -DOPT_LEVEL=0 Tasks/task1.cpp -o /tmp/task1_0 и т.д.
Данные собраны в Data/task1.csv (колонки N,O0,O1,O2,O3,noflag) и Data/task1_*.csv
График: task1.png - 5 кривых. O0 и noflag самые медленные (почти совпадают), O1 сильно быстрее, O2 и O3 близко к O1, иногда O3 чуть медленнее из-за агрессивной оптимизации.

Проблема с O3: если результат сортировки нигде не используется, компилятор может выкинуть весь код сортировки. Решение: volatile long long sum = 0; for(x:a) sum+=x;  или вывод элемента. Так компилятор видит что данные нужны.

Вывод: оптимизация дает ускорение в 5-10 раз для пузырька, самая безопасная -O2.

--------------------------------------------------------------------------------
ЗАДАНИЕ 2. Сложные быстрые сортировки O(N log N)
--------------------------------------------------------------------------------
Сделано: heap sort (куча), quick sort (Хоара, pivot посередине), merge sort (слияние).
Размеры: 1000, 5000, 10000, 20000, 50000, 100000, 200000.
Графики:
 - task2.png - три кривые, растут почти линейно, намного ниже чем O(N^2) на больших N.
 - task2_norm.png - зависимость t/(N log N) от N. Получается почти горизонтальная линия (константа), значит t ~ const * N log N. Так доказываем O(N log N).

Что рассказать: куча строит пирамиду за O(N) и N раз извлекает max за log N. Быстрая сортировка делит массив по pivot. Слияние рекурсивно делит пополам и сливает за O(N).

--------------------------------------------------------------------------------
ЗАДАНИЕ 3. Халк против Локи
--------------------------------------------------------------------------------
Сделано: все 6 сортировок (3 медленные + 3 быстрые) на одном графике при одинаковом диапазоне N=500..5000. Измерено для 4 уровней оптимизации O0..O3, поэтому 4 графика:
 - task3_O0.png, task3_O1.png, task3_O2.png, task3_O3.png - на каждом 6 кривых.
На всех видно: при N<1000 разница небольшая, при N=5000 быстрые в десятки раз быстрее медленных.

Табличка ускорения: Graph/task3_speedup.csv и task3_speedup.png
Среднее ускорение = среднее по N (t_O0 / t_Ox)
Пример:
 bubble: O0=1, O1=9.5x, O2=3.0x, O3=2.9x
 insertion: O0=1, O1=10.5x, O2=17.5x, O3=15x  (вставка сильно ускоряется)
 selection: O0=1, O1=2x, O2=8.3x, O3=7.7x
 heap: 5.7x, 7.2x, 6.9x
 quick: 2.2x, 2.8x, 2.7x
 merge: 3x, 3.6x, 3.5x
O2 чаще всего лучшее, O3 иногда чуть хуже.

Компиляция: g++ -O0 -DOPT_LEVEL=0 Tasks/task3.cpp -o /tmp/task3_0 && /tmp/task3_0  и т.д.

ЗАДАНИЕ 4. C++ против Python
--------------------------------------------------------------------------------
Сделано: те же 3 простые сортировки написаны на Python (bubble, insertion, selection) в Graph/graph4.py. В нем же измеряется время Python через time.perf_counter().
C++ данные: Tasks/task4.cpp генерит Data/task4_cpp.csv
Python данные: graph4.py генерит Data/task4_py.csv
Графики: task4_bubble.png, task4_insertion.png, task4_selection.png - на каждом две кривые C++ vs Python. Python в среднем в ~15 раз медленнее C++ на одинаковом N.
Размеры маленькие N=100..2000, потому что Python на больших N слишком долго.

Что рассказать: Python интерпретируемый, нет компиляции и оптимизации, циклы медленные.

--------------------------------------------------------------------------------
ЗАДАНИЕ 5. Зависимость от начальных данных
--------------------------------------------------------------------------------
Сделано: для каждого из 6 алгоритмов три случая: sorted (лучший), random (средний), reversed (худший). Размер N=500..5000.
Код: Tasks/task5.cpp создает 6 файлов Data/task5_bubble.csv ... task5_merge.csv, в каждом колонки N,sorted,random,reversed.
Графики: task5_bubble.png .. task5_merge.png  по одному на алгоритм, три кривые на каждом.

Наблюдения:
 - bubble: sorted почти 0 (один проход без обменов), reversed самый медленный.
 - insertion: sorted O(N) - самая быстрая, reversed O(N^2) - самая медленная, random посередине.
 - selection: все три почти одинаково (всегда O(N^2) сравнений).
 - heap, merge: все три почти одинаково O(N log N) не зависит от входных.
 - quick: sorted и reversed могут быть медленнее random если pivot неудачный (у нас pivot посередине, поэтому разница меньше, но все равно хуже random в теории).

Дополнительно task5_all_random.png - сравнение всех 6 на random данных.

--------------------------------------------------------------------------------
ЗАДАНИЕ 6. Королевская битва (накладные расходы)
--------------------------------------------------------------------------------
Сделано: измерены 4 операции отдельно:
 1) генерация массива случайных чисел,
 2) проход по массиву вперед (сумма a[i]*2+1),
 3) проход назад,
 4) вывод массива в файл (в /tmp/out_tmp.txt, чтобы не спамить экран).
Размеры: 10k, 50k, 100k, 200k, 500k, 1M.
Графики:
 - task6.png - 4 кривые линейные, вывод самый медленный (~0.05с на 1M), генерация вторая (~0.036с), проходы быстрые (~0.002с).
 - task6_loglog.png - лог-лог наклон 1 => O(N).

Проблема с таймером: chrono nanoseconds врет, точность ~ микросекунды, мелкие N дают ступеньки. Решение: повторять много раз и усреднять, для больших N reps=3, для мелких reps=5.

ЗАДАНИЕ 7. Халк против Локи, но поменьше (малые N)
--------------------------------------------------------------------------------
Сделано: те же 6 сортировок, но N=3..100 шаг 2. Для сглаживания каждая сортировка повторяется 2000-5000 раз на пуле из 100 случайных массивов, берется среднее время за одну сортировку. Генерация вынесена за пределы таймера, чтобы не мешать.

Дополнительно Python на малых N: в Graph/graph7.py измерен bubble на Python для N=3..100 (reps=1000). Графики task7_py_vs_cpp.png и task7_all_vs_py.png показывают что даже на малых N C++ быстрее Python в сотни раз, но относительная разница меньше чем на больших.

--------------------------------------------------------------------------------
ЗАДАНИЕ 8. Королевская битва, но поскучнее (разные типы)
--------------------------------------------------------------------------------
Сделано: сортировка std::sort для разных типов:
 char (1 байт), short (2), int (4), long long (8), struct Small {int a,b;}, struct Big {int a[16]; int key;}
Размеры: 1k,5k,10k,20k,50k,100k.
Графики:
 - task8.png - 6 кривых, char самый быстрый (мало памяти, хорошо в кэше), big самый медленный (копирование 16 интов при каждом swap).
 - task8_norm.png - нормировка на int (time / time_int), видно что char в ~0.5 раза быстрее, big в ~1.3 раза медленнее.

Объяснение: время сортировки зависит от размера элемента: чем больше байт, тем больше копирований, хуже кэш. Но есть нюансы: выравнивание, inline, оптимизации компилятора. Тяжелые структуры с статическими массивами сильно тормозят.
